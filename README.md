# ELM GROUP · מערכת עבודה למכירות

מערכת סגורה לניהול עבודת המכירות של ELM GROUP (AKIRA SEIKI · TAJMAC-ZPS):
- **היום שלי** — סדר יום, חיוג, ניווט, תיעוד מהיר ומשימות שבאיחור.
- **יומן ותכנון תקופה** — תצוגת חודש, שבוע ויום, ותוכנית שנבנית מתצוגה מקדימה ולא דורסת פגישות קיימות.
- **לקוחות וכרטיס לקוח** — כולל אתרים, אנשי קשר, אפיון טכני, מקור המידע ואימות.
- **הזדמנויות (Kanban)**, **מסלול יום שטח** ו**דוחות** — כל מספר בדוח נפתח לרשימת הרשומות שמרכיבות אותו.
- **ייבוא וניקוי נתונים** — מיפוי עמודות, זיהוי כפילויות ותור השלמות.
- **מחקר ומקורות** — הרחבת המאגר במקורות מתועדים.

**טכנולוגיה:** Next.js 15 (App Router, TypeScript), Tailwind 4, Supabase (Postgres, Auth, RLS). מותאם לפריסה ב-Vercel. כל החישובים לפי Asia/Jerusalem.

---

## 1. הקמת Supabase

1. **יצירת פרויקט:** צרו פרויקט חדש ב-[supabase.com](https://supabase.com). מומלץ לבחור אזור קרוב, למשל Frankfurt.
2. **הרצת ה-migrations:** אפשר בשתי דרכים, לפי הסדר:
   - **דרך ה-SQL Editor:** הדביקו והריצו את שלושת הקבצים שבתיקייה `supabase/migrations/`, לפי סדר שמותיהם.
   - **דרך ה-CLI:**
     ```bash
     npx supabase link --project-ref <PROJECT_REF>
     npx supabase db push
     ```
3. **Authentication → Sign In / Providers:**
   - **כבו** את האפשרות `Allow new users to sign up`. כך אין הרשמה ציבורית.
   - השאירו את Email מופעל.
4. **Authentication → URL Configuration:**
   - **Site URL:** כתובת ה-Vercel, למשל `https://elm-sales.vercel.app`.
   - **Redirect URLs:** הוסיפו `https://elm-sales.vercel.app/**`, ולפיתוח גם `http://localhost:3000/**`.
5. **Authentication → Email Templates.** כדי שקישורי ההזמנה והאיפוס יעבדו בצד השרת, החליפו את הקישור בתבניות:
   - **Invite user:**
     ```html
     <a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite&next=/set-password">הצטרפות למערכת</a>
     ```
   - **Reset Password:**
     ```html
     <a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery&next=/set-password">איפוס סיסמה</a>
     ```
6. **SMTP.** שירות המייל המובנה של Supabase מוגבל לכמה הודעות בשעה. לעבודה שוטפת הגדירו SMTP משלכם (Resend, SendGrid או Gmail Workspace) ב-Project Settings → Authentication → SMTP.
7. **המנהל הראשון (פעם אחת):**
   - ב-SQL Editor הריצו:
     ```sql
     insert into public.invitations (email, role, full_name)
     values ('your@email.com', 'admin', 'השם שלך');
     ```
   - ב-Authentication → Users לחצו **Invite user** והזינו את אותה כתובת.
   - אחרי הכניסה הראשונה תגדירו סיסמה ותהיו מנהלים.
   - את שאר המשתמשים מזמינים מתוך המערכת, במסך **משתמשים**.

> **למה ההזמנה נרשמת קודם?** הפרופיל של משתמש נוצר פעיל רק אם קיימת לו רשומה ב-`invitations`. גם אם ההרשמה הציבורית תופעל בטעות, משתמש לא מוזמן מקבל פרופיל לא פעיל ואינו רואה שום נתון.

## 2. פריסה ב-Vercel

1. **העלאה:** העלו את הפרויקט ל-GitHub (קובץ `.env.local` לא עולה, הוא ב-`.gitignore`). ב-Vercel בחרו New Project ← ייבוא ה-repo. ה-Framework יזוהה אוטומטית כ-Next.js.
2. **משתני סביבה:** הזינו ב-Settings → Environment Variables (הערכים נמצאים ב-Supabase → Project Settings → API):

   | משתנה | ערך | הערה |
   |---|---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | ה-Project URL | |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | מפתח ה-anon / publishable | ציבורי מטבעו; הגנת הנתונים היא ב-RLS |
   | `SUPABASE_SERVICE_ROLE_KEY` | מפתח ה-service_role / secret | **סודי.** בלי קידומת `NEXT_PUBLIC`. משמש רק להזמנת משתמשים, בצד השרת ואחרי בדיקת הרשאת מנהל |
   | `NEXT_PUBLIC_SITE_URL` | כתובת האתר, למשל `https://elm-sales.vercel.app` | |

3. **פריסה ראשונה:** לחצו Deploy. אחר כך עדכנו את Site URL ב-Supabase לכתובת שהתקבלה, אם עדיין לא עשיתם זאת.
4. **לוגו וצבע:**
   - הלוגו נמצא בקובץ `public/logo.jpg`.
   - צבע המותג מוגדר ב-`src/app/globals.css`. הוורוד של הלוגו הוא `#F80593`. לכפתורים ולטקסט משמש גוון כהה מעט (`#D6047F`), כדי לשמור על ניגודיות קריאה.

## 3. הפעלה ראשונה

1. **ייבוא:** היכנסו כמנהל ← **ייבוא** ← העלו את קובץ הלקוחות. בדקו את המיפוי ואת התצוגה המקדימה, ואשרו.
2. **השלמות:** במסך **איכות נתונים** עברו על הכפילויות האפשריות (13 בקובץ המקורי) ועל תור ההשלמות.
3. **שיוך:** במסך **לקוחות** סמנו לקוחות ושייכו אותם לאיש מכירות. איש מכירות רואה רק את מה ששויך אליו.
4. **תכנון:** במסך **תכנון תקופה** בחרו חודש או תקופה ← **תצוגה מקדימה** ← **שמירת התוכנית**.
5. **מחקר:** אפשר לטעון את קובץ המחקר `data/research_leads_2026-11-04.csv` במסך **מחקר ומקורות**. כל מקור נבדק ומאושר בנפרד, ושום לקוח לא נוצר אוטומטית.

## 5. בדיקות

```bash
npx vitest run tests/unit.test.ts     # ניתוח כתובות, סיווג, טלפונים, ייבוא הקובץ האמיתי, מנוע התכנון
IT_SUPABASE_URL=... IT_ANON_KEY=... npx vitest run tests/integration.test.ts
```

**מה בודקות בדיקות האינטגרציה:**
- **הרשאות:** RLS, משתמש לא מוזמן ומשתמש אנונימי, ניסיון לערוך רשומה של אחר, העלאת הרשאות לעצמי ואיחוד רשומות ע״י מי שאינו מנהל.
- **ייבוא:** ייבוא מלא, ייבוא חוזר ללא כפילויות, ושינוי נתונים שנכנס לבדיקה ולא נדרס.
- **כפילויות ואיחוד:** סריקת כפילויות ואיחוד ידני.
- **תכנון:** שבועות חלקיים, 3 שיחות ביום לחברות שונות שאינן חברת הביקור, ו-3 ימי שטח בשבוע.
- **שמירה:** שמירת תוכנית ללא דריסת ביקור מתואם, ושמירת נתונים אחרי כניסה מחדש.

**דרישות:**
- **משתמשי בדיקה:** `admin@elm.test`, `dana@elm.test`, `yossi@elm.test` (מוזמנים) ו-`intruder@elm.test` (לא מוזמן), כולם עם הסיסמה `Test-Password-123`.
- **מסד נפרד:** הבדיקות כותבות נתונים, ולכן **אין להריץ אותן על מסד הייצור.**

**סביבה מקומית:** בתיקייה `scripts/local-stack/` נמצאים הקבצים להרמת Postgres + Supabase Auth + PostgREST בלי Docker, ותסריט בדיקת קצה-לקצה בדפדפן (`e2e.py`, Playwright).

**תוצאות ההרצה האחרונה:** 22 בדיקות יחידה ו-11 בדיקות אינטגרציה עברו. גם תרחיש הדפדפן המלא עבר: ייבוא, תכנון, תיעוד שיחה, יומן, כרטיס לקוח, הזדמנות, דוחות וחסימת דפי מנהל.

## 6. אבטחה — מה נאכף ואיפה

- **שכבת השרת:**
  - כל הדפים, פעולות השרת ונתיבי ה-API מוגנים במידלוור, שמאמת את המשתמש מול Supabase.
  - בכל דף ובכל פעולה נבדק שוב שהמשתמש פעיל, ובפעולות מנהל שהוא מנהל.
- **שכבת המסד (RLS):** אנונימי לא רואה כלום. משתמש לא פעיל לא רואה כלום. איש מכירות רואה ומעדכן רק את הלקוחות שלו ואת מה שתלוי בהם: אתרים, אנשי קשר, הזדמנויות, פעולות והערות.
- **פעולות מנהל בלבד, גם במסד:** העברת רשומה לאיש מכירות אחר, שינוי תפקיד, ייבוא, טיפול בכפילויות, איחוד רשומות וקריאת יומן השינויים.
- **תיעוד:** לכל רשומה נשמרים `created_by/at` ו-`updated_by/at`, וכל שינוי נרשם ב-`audit_log` כולל ערכים לפני ואחרי.
- **פרטיות:** אין דף ציבורי, האתר מסומן `noindex`, ומפתח השירות לא נחשף לדפדפן.

## 7. מגבלות ידועות

- **זמני נסיעה** הם הערכה לפי מרחק אווירי בין מרכזי יישובים. אין חיבור לשירות מסלולים, ולכן אין אופטימיזציית מסלול. הניווט עצמו נפתח ב-Waze או ב-Google Maps.
- **זיהוי יישוב** מתבסס על מילון של 91 יישובים וכינויים נפוצים. כתובת עם כמה יישובים, או עם יישוב שלא זוהה, מסומנת לבדיקה. 24 רשומות בקובץ המקורי לא זוהו.
- **הנתונים בקובץ המקורי ישנים:** כ-190 כתובות הן תיבות דואר, ו-468 רשומות בלי איש קשר. כל הרשומות יובאו כ"פוטנציאלי · לא מאומת". בעמודת האימייל נמצאו 53 הערות שיחה ישנות ("לא מעוניין", "מספר שגוי"). הן נשמרו כהערות, ורשומות שסומנו "לא מעוניין" קיבלו עדיפות נמוכה.
- **הלקוחות לא משויכים:** בקובץ אין מידע על איש מכירות אחראי, ולכן השיוך נעשה ידנית במסך הלקוחות.
- **מחקר ברשת:** בוצע מחקר ראשוני שהניב 27 מקורות, כולם ממדריכים עסקיים, בעיקר b144. לא אומת אף מקור מול אתר החברה עצמה, ובחלק מהשורות הטלפון הוא כנראה מספר הפניה של המדריך. אזורי הקריות, כרמיאל, יוקנעם, נתניה והדרום לא כוסו. זו אינה רשימה מלאה של המפעלים בארץ.
- **שליחה וזימון:** המערכת לא שולחת הודעות ללקוחות, לא מתקשרת ולא מזמינה פגישות. כפתור "חיוג" פותח את החייגן בנייד, וההחלטה נשארת בידיכם.
- **חגים** לא נטענים אוטומטית. מוסיפים אותם כ"חג" במסך התכנון.
- **מחיקת חשבון משתמש** נעשית בלוח הבקרה של Supabase. במערכת אפשר להשבית משתמש.
